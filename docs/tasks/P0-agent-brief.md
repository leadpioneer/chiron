- **Статус:** готово к исполнению
- **Дата:** 24.10.2026
- **Владелец продукта:** автор проекта
- **Обязательное чтение:** `AGENTS.md`, `docs/decisions/v1-decisions.md`,

  `docs/decisions/ADR-002-reschedule-and-cycle-review.md`.

## Цель P0

Закрыть критический контур перед alpha:

1. Перенос тренировки без изменения плана.
2. Возвращение после короткой паузы.
3. Пересмотр цикла после длинной паузы или болезни.
4. Полный цикл в тестах, а не только первые сессии.
5. E2E-тесты в репозитории и CI.

## Что не входит в P0

- Telegram Mini App на реальных устройствах и живой бот.
- Живой LLM-провайдер, платный бюджет, сравнение моделей.
- Staging/продакшн-деплой, юридические документы, 152-ФЗ.
- Сплиты на 3+ дня, выбор произвольных упражнений, настройки оборудования.
- Редизайн интерфейса.
- Изменение порогов прогрессии, safety-словарей и промптов без отдельного
  подтверждения.

## Инварианты

1. План неизменяем. Любое изменение — новая `plan_version`, связанная с
   `decision` и `audit_event`.
2. Перенос даты не меняет назначения и не создаёт версию плана.
3. Нет автоматического повышения нагрузки после паузы: возврат и пересборка
   только после подтверждения.
4. Safety важнее прогрессии. Красный флаг останавливает тренировку.
5. Одно решение меняет один параметр одного упражнения; возврат и пересборка —
   отдельные сценарии с явной областью.
6. Все даты — ISO `YYYY-MM-DD`; расчёты в UTC.
7. Тесты не должны работать с рабочей БД. Использовать `TEST_DATABASE_URL` или
   отдельную базу `chiron_test`.

## Задачи

### P0-1. Схема и миграция

Добавить в `packages/db/src/schema.ts`:

- `training_cycles.return_phase_sessions` integer not null default 0;
- `training_cycles.close_reason` text nullable;
- `sessions.rescheduled_from` date nullable;
- `sessions.is_return` boolean not null default false.

Сгенерировать миграцию `0002_*`, применить на чистой БД, проверить
`db:seed`.

**Приёмка:** миграция применяется с нуля; существующие циклы не ломаются;
`npm run typecheck` проходит.

### P0-2. Backend переноса

Добавить контракт:

```ts
{
  newDate: "YYYY-MM-DD",
  mode: "SINGLE" | "SHIFT_TAIL" // default SINGLE
}
```

Сервис `rescheduleSession(userId, sessionId, input)`:

- только `PLANNED`;
- `newDate >= today`;
- `newDate <= cycle.end_date + 14 дней`;
- `SINGLE`: если `newDate >= next planned session date` → `409 ORDER_CONFLICT`;
- `SHIFT_TAIL`: сдвинуть текущую и все последующие `PLANNED` сессии на
  `deltaDays`; сдвинуть `end_date`; суммарное продление не более 14 дней от
  базовой длины 8 недель;
- `rescheduled_from` сохраняет первую исходную дату;
- audit `SESSION_RESCHEDULED` с `from`, `to`, `mode`, `deltaDays`,
  `endDateBefore`, `endDateAfter`;
- версия плана не создаётся.

API: `POST /api/sessions/:id/reschedule`.

**Приёмка:** тесты на SINGLE, ORDER_CONFLICT, SHIFT_TAIL, лимит 14 дней,
запрет для IN_PROGRESS/COMPLETED/SKIPPED.

### P0-3. UI переноса

- Кнопка «Отложить» на «Сегодня» рядом с «Начать» и «Пропустить».
- Модальное окно: дата, режим, объяснение последствий.
- При `ORDER_CONFLICT` показать «Сдвинуть оставшиеся» и повторить с

- После успеха обновить «Сегодня».
- На мобильном 390×844 кнопки не перекрываются.

**Приёмка:** E2E-перенос одной сессии и сдвиг хвоста; audit виден в истории.

### P0-4. Пауза и возврат

Сервис `getPauseState(userId, cycle)`:

- 0–7 дней → `NONE`;
- 8–13 → `RETURN_1`;
- 14–27 → `RETURN_2`;
- ≥28 → `LONG`;
- активная safety-пауза/болезнь → `SAFETY`.

Для `RETURN_1`/`RETURN_2` на «Сегодня» показать карточку:

- сколько дней пауза;
- «было → станет» по нагрузке;
- RIR 3–4;
- прогрессия заблокирована.

Кнопка «Подготовить возвращение» вызывает
`POST /api/sessions/:id/return`, который:

- создаёт новую версию плана copy-on-write;
- `RETURN_1`: −5% к внешнему весу, +1 шаг к помощи гравитрона, целевой RIR 3,
  `is_return=true` для одной сессии;
- `RETURN_2`: −10%, RIR 4, `is_return=true` для двух следующих сессий;
- не меняет упражнения и роли;
- пишет decision и audit.

Правила рекомендаций получают `returnPhase`:

- при `returnPhase=true` — `HOLD`, правило `RETURN_PHASE`, без прогрессии;
- safety-сигналы по-прежнему имеют приоритет.

**Приёмка:** оба режима, отсутствие прогрессии, RIR на UI, audit, тест на
недопустимость повторного возврата без новой паузы.

### P0-5. Пересмотр после длинной паузы

Триггеры: пауза ≥ 28 дней, safety-пауза ≥ 14 дней, ручной запрос.

На «Сегодня» вместо старта — экран «Цикл нужно пересмотреть»:

- причина и дата последней тренировки;
- два действия: «Пересобрать цикл» и «Завершить цикл»;
- никакого автоматического старта.

API: `POST /api/cycles/:id/review`
`{ action: "REBUILD" | "STOP", reason: "LONG_PAUSE" | "ILLNESS" | "USER" }`.

`REBUILD`:

- старый цикл → `STOPPED`, `close_reason`;
- новый цикл на 8 недель с теми же вариантами, подсобкой и эстетикой;
- нагрузки из последней версии × множитель возврата (4–6 недель 90%,
  7–12 — 80%, 13–24 — 70%, >24 — калибровка);
- `return_phase_sessions = 4`, первые 4 сессии `is_return=true`;
- audit `CYCLE_REVIEWED`, `CYCLE_REBUILT`.

`STOP`:

- старый цикл → `STOPPED`/`INCOMPLETE`;
- переход в онбординг;
- audit.

**Приёмка:** пауза ≥28 блокирует старт; REBUILD создаёт новый цикл и возвратную
фазу; STOP ведёт в онбординг; повторный вызов не создаёт дубль.

### P0-6. Полный цикл в тестах

Добавить `npm run test:cycle` и детерминированный сценарий:

1. Создать тестового пользователя и цикл «через день».
2. Пройти 28 сессий: заполнять подходы на верхней границе, принимать
   рекомендации, проверять независимую прогрессию.
3. Смоделировать снижение в двух основных → проверить `DELOAD`.
4. Завершить цикл; проверить `COMPLETED`, версии плана, audit.
5. Перейти к следующему циклу; проверить новые нагрузки.
6. Повторить для 5-дневной схемы (23 сессии).

Требования:

- отдельная тестовая БД;
- никаких реальных дат/сна;
- тест не должен зависеть от текущего времени;
- вывод: число сессий, версий плана, решений, audit-событий.

**Приёмка:** `npm run test:cycle` проходит на чистой тестовой БД; падение
теста означает блокировку P0.
