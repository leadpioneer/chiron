# ADR-003 — Alpha security и эксплуатация

- **Статус:** принято
- **Дата:** 25.10.2026
- **Владелец:** автор проекта
- **Связанные документы:** [`v1-decisions`](v1-decisions.md),
  [`ADR-002`](ADR-002-reschedule-and-cycle-review.md),
  [`P1-agent-brief`](../tasks/P1-agent-brief.md)

## Контекст

P0 закрыл тренировочный контур. До допуска тестеров нужно закрыть вход,
доставку magic link, бюджет LLM, staging и восстановление данных. Публичной
регистрации нет: тестеры входят через allowlist.

## Решения

### 1. Вход и сессия

- **Magic link:** один токен — одно использование; срок 15 минут; в БД
  хранится только SHA-256 хэш.
- **Rate limit:** не более 5 ссылок на email за 15 минут и не чаще одной
  ссылки в 30 секунд. Ответ при превышении — `429` с `Retry-After`. IP-лимит
  auth-маршрутов — 120 запросов за 15 минут на процесс.
- **Сессия:** stateless JWT в httpOnly cookie, `SameSite=Lax`, `Secure` в
  production, абсолютный срок 30 дней и ротация раз в 7 дней через proxy.
- **CSRF:** для небезопасных методов проверяется `Origin` (или `Referer`),
  если он передан. Разрешены `APP_URL`, текущий origin и `ALLOWED_ORIGINS`.
  Запрос без `Origin`/`Referer` допускается для серверных клиентов; cookie
  остаётся защищена `SameSite=Lax`.
- **`AUTH_DEV_MODE`:** в production игнорируется и запрещён при старте.
  Демо-вход и возврат ссылки в ответе доступны только вне production.
- **Alpha-допуск по email:** `ALPHA_EMAIL_ALLOWLIST` — точные адреса или
  `*@domain`. Новый email вне списка получает `403 EMAIL_NOT_ALLOWED`;
  существующие пользователи входят без ограничения. Пустой список в
  production блокирует новые email-регистрации; в production должен быть задан
  хотя бы один allowlist — email или Telegram.
- **Удаление аккаунта:** soft delete анонимизирует email и удаляет
  identities. Тот же magic link не восстанавливает удалённого пользователя:
  ссылка отклоняется с `account_deleted`. Повторная регистрация на тот же
  email создаёт новый аккаунт, потому что старый email уже анонимизирован.
- **Очистка:** использованные и истёкшие magic links старше 24 часов
  удаляются при новых запросах и командой `npm run db:cleanup`.

### 2. Email

- Провайдер выбирается через `EMAIL_PROVIDER`:
  - `resend` — HTTP API Resend, без новой зависимости;
  - `webhook` — совместимый с P0 webhook `{to, url}`;
  - `console` — только разработка, письмо не отправляется;
  - `none` — доставка отключена.
- В production `console` запрещён. Явный `EMAIL_PROVIDER=none` разрешён для
  Telegram-only alpha: форма email скрыта, `request-link` отвечает `503`.
- Письмо содержит текст и HTML, срок действия и предупреждение «если это были
  не вы — игнорируйте».
- При ошибке доставки созданная ссылка удаляется, пользователь получает
  `502`/`503` без деталей провайдера.

### 3. Telegram

- `initData` Mini App проверяется по HMAC и `auth_date` ≤24 часов.
- Login Widget проверяется по SHA-256 от bot token; данные старше 24 часов
  отклоняются.
- `TELEGRAM_ALLOWLIST` — список username (без `@`) и/или числовых id через
  запятую. Если список задан, новые Telegram-пользователи вне списка
  получают `403`. Уже связанные identities не блокируются.
- Связка Telegram с существующим Web-аккаунтом по короткому коду требует
  bot webhook и отдельного хранилища кодов. Это P1-B, не P1-A.
- Напоминания: cron в 16:00 `Europe/Moscow`, только `PLANNED`-сессии на
  сегодня, идемпотентность через audit `REMINDER_SENT`.
- Inline-кнопка `postpone:<sessionId>` обрабатывается webhook с проверкой
  `X-Telegram-Bot-Api-Secret-Token`, Telegram identity и владельца сессии.
- Исходящие вызовы Telegram API на staging идут через
  `TELEGRAM_PROXY_URL`; тело запроса — UTF-8 JSON.

### 4. LLM

- LLM остаётся парсером и объяснением; план и БД она не пишет.
- Для alpha активен routerai (OpenAI-совместимый `/chat/completions`), модель
  `~deepseek/deepseek-v4-flash-latest`; см.
  [`ADR-005`](ADR-005-llm-provider-routerai.md). Gemini остаётся
  альтернативным провайдером.
- `LLM_ENABLED=0` — kill switch: все вызовы обслуживает локальный парсер.
- Safety-наблюдения LLM неавторитетны: сервер объединяет их с
  детерминированными правилами, red нельзя понизить. LLM-метки используются
  только как дополнительный сигнал.
- Бюджеты: per-user дневной и месячный, плюс глобальный месячный
  `LLM_GLOBAL_MONTHLY_BUDGET_USD`. При превышении — локальный fallback.
- Порог алерта — 80% любого бюджета; событие пишется в лог в JSON без PII.
- Golden dataset — 50 кейсов. Гейт: red recall 100%, yellow recall ≥95%,
  numeric accuracy ≥98%, invalid JSON ≤0,5%, scope compliance 100%.
- `npm run test:llm-eval` проверяет локальный парсер детерминированно;
  живой прогон включается `LLM_EVAL_LIVE=1` и требует ключ.

### 5. Индексация

- Alpha-домен закрыт от индексации на трёх уровнях: `robots.txt` с
  `Disallow: /`, `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet,
  noimageindex` на всех ответах и meta robots в HTML.
- Домен не добавляется в поисковые панели; ссылки на staging не публикуются
  в индексируемых местах.
- Это не заменяет аутентификацию: доступ к данным всё равно требует сессии.

### 6. Staging и данные

- Staging — отдельные PostgreSQL и приложение, TLS через Caddy, закрытый
  прямой порт приложения.
- `/api/health` проверяет БД и отдаёт состояние LLM без секретов.
- Миграции и seed выполняются отдельным bootstrap-контейнером.
- Бэкап — `pg_dump --format=custom`, retention 14 дней, опциональная копия в
  S3-совместимое хранилище через rclone.
- Restore требует явного `RESTORE_CONFIRM=YES` и запрещён для production-БД
  без `ALLOW_PROD_RESTORE=1`.
- Восстановление проверяется на staging до допуска тестеров.

## Последствия

- P1-A не требует миграций и новых runtime-зависимостей.
- Один инстанс приложения достаточен для alpha; при горизонтальном
  масштабировании IP-лимиты нужно перенести в общий store.
- Связка Telegram и Web-аккаунта, реальные устройства и юридические документы
  остаются в P1-B.
