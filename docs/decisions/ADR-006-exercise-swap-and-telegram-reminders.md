# ADR-006 — Замена упражнений и напоминания в Telegram

- **Статус:** принято
- **Дата:** 25.10.2026
- **Владелец:** автор проекта
- **Связанные документы:** [`v1-decisions`](v1-decisions.md),
  [`ADR-003`](ADR-003-alpha-security-and-operations.md),
  [`ADR-005`](ADR-005-llm-provider-routerai.md)

## Контекст

В RDL-день нужен подсобный ягодичный мостик. Пользователь должен менять не
только нагрузку, но и само упражнение — основное или подсобное — из каталога.
Также нужны Telegram-напоминания о тренировке в 16:00 МСК с кнопкой
«Отложить на завтра». Все изменения плана обязаны оставаться copy-on-write и
попадать в decision/audit.

## Решения

### 1. Ягодичный мостик

- В библиотеке `RU-free-exercise-db` уже есть `Barbell_Glute_Bridge`.
- Добавлен curated exercise `glute_bridge` и вариант
  `barbell_glute_bridge` (штанга, внешняя нагрузка, шаг 5 кг).
- В шаблоне `pull_push_2x`, в блоке `posterior_chain`, добавлено подсобное
  упражнение `bridge`: 2 × 8–12, цель 10, RIR 2, `supportsPrimaryId`
  румынской тяги. Оно включено в шаблон по умолчанию и помечено
  `optional=true`, чтобы в UI была плашка «необязательно».
- Новые циклы получают мостик автоматически. Старые версии планов не
  переписываются.

### 2. Замена упражнения

- В UI сессии для `PLANNED`-тренировки есть кнопка «Заменить» у каждого
  упражнения.
- API `GET /api/exercises` отдаёт curated-варианты с `blockKey` и
  `primaryEligible`; API
  `POST /api/prescriptions/:id/replace` принимает `variantId`.
- Допустима замена только на вариант того же блока. Для роли `PRIMARY`
  доступны только базовые варианты (`primaryEligible`).
- Замена создаёт:
  - новую `plan_version` (copy-on-write всех блоков и назначений);
  - синтетическую принятую рекомендацию `MANUAL_EXERCISE_SWAP`;
  - `decision` с `outcome=EDITED`, `reasonCategory=EXERCISE_SWAP`;
  - `audit_event` `PLAN_VERSION_CREATED` с действием `EXERCISE_REPLACED`.
- Нагрузка нового упражнения — `null`: вес, помощь и добавка не переносятся
  между разными движениями. Подходы, диапазон повторений и RIR сохраняются.
- `supportsPrimaryId` и `target_blocks.primary_prescription_id` переносятся на
  новые копии. Pending-рекомендации, которые ссылались на заменённое
  назначение, истекают; остальные переносятся на новые ID.
- История нового варианта начинается заново; сравнивать подходы старого и
  нового упражнения нельзя.
- Замена доступна только при наличии `PLANNED`-сессии; текущая сессия должна
  быть не начата.

### 3. Напоминания

- Ежедневно в 16:00 `Europe/Moscow` cron запускает
  `scripts/send-reminders.mts`.
- Напоминание получают только пользователи с привязанным Telegram identity и
  `PLANNED`-сессией на сегодня в активном цикле.
- Текст минималистичный: `Сегодня тренировка «Тяни»` или `«Толкай»`; список
  упражнений не отправляется. Две inline-кнопки: «Отложить на завтра»
  (`postpone:<sessionId>`) и «Окей» (`dismiss:<sessionId>`), которая удаляет
  сообщение.
- Идемпотентность: после отправки пишется audit-событие `REMINDER_SENT` с
  датой; повторный запуск в тот же день не дублирует сообщение.
- Webhook `POST /api/telegram/webhook` проверяет
  `X-Telegram-Bot-Api-Secret-Token`, находит Telegram identity, проверяет
  владельца сессии и переносит одну сессию на завтра через
  `rescheduleSession`. Ответ и редактирование сообщения идут через
  Telegram API.
- Тестовый режим `--test-telegram-id=<id>` отправляет сообщение только
  указанному id с кнопкой `postpone_test`; реальные пользователи не
  затрагиваются.
- Исходящие вызовы Telegram API идут через `TELEGRAM_PROXY_URL`
  (`http://127.0.0.1:2080` на staging), потому что прямой маршрут с сервера
  недоступен. Тело запроса — UTF-8 JSON, поэтому кириллица не превращается в
  `?`.

## Последствия

- Миграции не требуются.
- Новые циклы включают мостик; существующие планы не меняются.
- Замена упражнения всегда оставляет след в плане, решении и audit.
- Напоминания требуют установленного webhook и cron; без Telegram identity
  пользователь не получает сообщений.
- Browser Login Widget по-прежнему требует `/setdomain` в BotFather; Mini App
  и напоминания от этого не зависят.

## Альтернативы

1. **Менять упражнение на месте, без новой версии.** Отклонено: нарушает
   immutability и audit.
2. **Переносить нагрузку на новое упражнение.** Отклонено: разные движения и
   оборудование, это выдало бы догадку за данные.
3. **Отправлять напоминания из GitHub Actions.** Отклонено: нужен доступ к
   серверной БД и секретам; cron на сервере проще и ближе к данным.
4. **Использовать `getUpdates` вместо webhook.** Отклонено: кнопка должна
   обрабатываться сразу, webhook даёт адресный callback.
