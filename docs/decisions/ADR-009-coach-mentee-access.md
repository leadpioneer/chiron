# ADR-009 — Режим подопечного: доступ тренера к дневнику

- **Статус:** принято; реализовано и задеплоено 25.10.2026 (`2b20812`)
- **Дата:** 25.10.2026
- **Владелец:** автор проекта
- **Связанные документы:**
  [`ADR-003`](ADR-003-alpha-security-and-operations.md),
  [`ADR-007`](ADR-007-tma-only-and-personal-data-scope.md),
  [`ADR-008`](ADR-008-user-control-and-corrections.md),
  [`P2-agent-brief`](../tasks/P2-agent-brief.md)

## Контекст

Владелец ведёт дневник для себя и хочет заполнять, менять и читать дневник
близкого человека (Даши). Общий логин не подходит: он не даёт разделения
«кто сделал», отзыва доступа и безопасной передачи аккаунта. Нужен явный
режим тренера.

## Решения

### 1. Отдельный профиль подопечного

- Подопечный — отдельная запись `users` со своим `id`, профилем, циклами,
  тренировками и аудитом.
- Профиль может быть создан без логина (managed profile).
- При создании можно сразу привязать Telegram ID из allowlist. Тогда при
  входе в TMA подопечный попадает в этот же профиль, а не создаёт второй.
- Если Telegram ID не привязан, вход подопечного откладывается до привязки.

### 2. Связь тренера и подопечного

Таблица `coach_mentees`:

- `coach_user_id`, `mentee_user_id`;
- `status` (`ACTIVE` / `REVOKED`);
- `permissions` (`WRITE`; чтение всегда разрешено);
- уникальная пара, каскадное удаление.

Тренер видит только активные связи. Отзыв доступа не удаляет дневник.

### 3. Контекст subject

- `viewer` — кто вошёл; `subject` — чей дневник открыт.
- По умолчанию `subject = viewer`, поэтому обычный сценарий не меняется.
- Переключение хранится в httpOnly cookie `chiron_subject`.
- Все тренировочные страницы и API используют `subject.id`; auth, выход,
  удаление аккаунта остаются на `viewer`.
- Если cookie указывает на неактивную связь, страница уводит в
  `/mentees?error=access`, API отвечает `403 SUBJECT_FORBIDDEN`.
- `READ`-связи блокируют мутации ответом `403 READ_ONLY`.

### 4. Аудит

- `audit_events.user_id` — чей дневник изменён.
- `audit_events.actor_user_id` — кто изменил (тренер или сам пользователь).
- Для старых событий `actor_user_id` может быть `null`; это означает
  «actor = user_id».
- Все изменяющие сервисы передают actor из контекста; Telegram-напоминания
  пишут actor = subject.

### 5. Интерфейс

- Пункт **«Подопечные»** в верхней навигации и **«Люди»** в нижней.
- `/mentees`: список, создание managed profile, выбор Telegram ID, открыть
  дневник, убрать доступ.
- При выборе подопечного — плашка «Дневник Даши · вы действуете как тренер»
  и кнопка «Вернуться в мой дневник».
- Все существующие страницы (`/today`, `/sessions`, `/history`,
  `/recommendations`, `/settings`, `/onboarding`) работают с subject без
  дублирования экранов.

### 6. Telegram-бот

- Бот остаётся per-identity: напоминание идёт тому, чей Telegram привязан к
  профилю.
- В callback нет subjectId; тренерский режим работает только в TMA/сайте.
- Если подопечный не привязан к Telegram, напоминаний у него нет.

### 7. Безопасность и границы

- Нельзя войти «как подопечный» через общий пароль.
- Тренер не может удалить аккаунт подопечного или изменить его вход.
- Отзыв доступа действует сразу: следующая страница/API уже не видит subject.
- Подопечный может позже получить свой вход через привязанный Telegram ID.
- Safety-правила не меняются: тренер не обходит красные флаги и паузы.

## Последствия

- Миграция `0003_dusty_skullbuster.sql`: `coach_mentees`, nullable
  `audit_events.actor_user_id`.
- Новые API: `/api/mentees`, `/api/mentees/[id]/revoke`, `/api/subject`.
- Новые E2E: `tests/e2e/mentees.spec.ts`.
- Доменная логика тренировок не менялась — изменился только контекст и права.

## Осталось

- Указать реальный Telegram ID Даши при создании профиля.
- READ-доступ и отдельный отчёт-дашборд, если понадобится.
- Claim-поток для случая, когда Telegram ID не был указан заранее.
- Проверка новых экранов на iPhone.
