# ADR-002 — Перенос тренировки и пересмотр цикла после паузы

- **Статус:** принято
- **Дата:** 24.10.2026
- **Контекст:** двухдневный сплит, схемы «через день» и
  «треня–отдых–треня–отдых–отдых»; пользователь может отложить тренировку;
  после длительной паузы, включая болезнь, цикл пересматривается.

## 1. Термины

- **Плановая сессия** — сессия со статусом `PLANNED`.
- **Последняя экспозиция** — последняя завершённая сессия (`COMPLETED`) с
  непустым `actual_date`.
- **Пауза** — число дней между последней экспозицией и сегодняшней датой. Если
  завершённых сессий нет, пауза считается от `training_cycles.start_date`.
- **Короткий перенос** — изменение плановой даты без изменения цикла.
- **Длинная пауза** — пауза ≥ 28 дней.
- **Safety-пауза** — активное решение `PAUSE`, красный флаг или болезнь,
  которая не позволяет продолжать тренировки.

## 2. Перенос тренировки

### 2.1. Разрешённые состояния

Перенос доступен только для `PLANNED` сессии. Для `IN_PROGRESS`,
`COMPLETED`, `SKIPPED` — `409`.

Новая дата:

- не раньше сегодняшней;
- не позже `cycle.end_date + 14 дней`;
- если перенос выходит за эти границы — только через пересмотр цикла.

### 2.2. Два режима

**`SINGLE`** — меняется только одна сессия.

- Если новая дата раньше плановой даты следующей сессии — сохраняется
  последовательность.
- Если новая дата совпадает или позже следующей сессии — `409
  ORDER_CONFLICT`; UI предлагает режим `SHIFT_TAIL`.
- Назначения упражнений не меняются; версия плана не создаётся.

**`SHIFT_TAIL`** — сдвигаются эта сессия и все последующие `PLANNED` сессии на
одинаковую дельту дней.

- `end_date` цикла сдвигается на ту же дельту.
- Максимальное суммарное продление цикла — 14 дней. Если больше — цикл
  пересматривается, а не продлевается.
- Назначения упражнений не меняются; версия плана не создаётся.

Оба режима пишут `audit_event` `SESSION_RESCHEDULED` с `from`, `to`, `mode`,
`deltaDays`, `cycleEndDateBefore`, `cycleEndDateAfter`.

### 2.3. Короткая пауза

- 0–7 дней: перенос без изменения нагрузки.
- 8–13 дней: следующий сеанс — `RETURN_1`: вес −5%, целевой RIR 3, прогрессия
  заблокирована на одну сессию.
- 14–27 дней: следующий сеанс — `RETURN_2`: вес −10%, RIR 4, затем ещё одна
  сессия с RIR 3; прогрессия заблокирована на две сессии.

`RETURN_1`/`RETURN_2` оформляются как рекомендация с подтверждением
пользователя и новой версией плана. Это не автоматическое изменение.

## 3. Длинная пауза и болезнь

### 3.1. Когда требуется пересмотр

Пересмотр обязателен, если:

- пауза ≥ 28 дней;
- активная safety-пауза длится ≥ 14 дней;
- пользователь сам нажал «Пересмотреть цикл»;
- после болезни пользователь сообщил, что не готов продолжать текущий цикл.

До пересмотра кнопка «Начать тренировку» недоступна. Вместо неё — экран
«Цикл нужно пересмотреть».

### 3.2. Варианты пересмотра

1. **Пересобрать цикл** (по умолчанию).
   - Старый цикл закрывается со статусом `STOPPED` и
     `close_reason = LONG_PAUSE` (или `ILLNESS`).
   - Создаётся новый цикл на 8 календарных недель с теми же вариантами,
     подсобкой и эстетикой.
   - Стартовые нагрузки берутся из последней подтверждённой версии плана и
     умножаются по правилам возвращения:
     - 4–6 недель — 90%;
     - 7–12 недель — 80%;
     - 13–24 недель — 70%;
     - > 24 недель — калибровка, без подстановки веса.
   - Первые 4 сессии нового цикла — фаза возвращения: RIR 3–4, прогрессия
     заблокирована. После четырёх сессий — обычные правила.
   - Пользователь подтверждает создание нового цикла.
2. **Завершить цикл**.
   - Старый цикл закрывается как `INCOMPLETE` или `STOPPED`.
   - Пользователь переходит в онбординг и может собрать новый цикл вручную.

Никакого автоматического продолжения после длинной паузы нет.

### 3.3. Болезнь и красные флаги

- Красный флаг → тренировка останавливается, тренировочные рекомендации
  приостанавливаются, предлагается неотложная помощь. Пересмотр цикла не
  заменяет медицинскую оценку.
- Болезнь без красных флагов → `PAUSE`; после выздоровления пользователь
  подтверждает пересмотр. Если пауза < 28 дней, допускается возвращение по
  правилам 2.3; если ≥ 28 дней — пересборка.
- Приложение не решает, «можно ли тренироваться» после болезни. Оно только
  предлагает консервативный возврат или паузу.

## 4. Данные и версии

Добавить:

- `training_cycles.return_phase_sessions` integer not null default 0;
- `training_cycles.close_reason` text nullable;
- `sessions.rescheduled_from` date nullable;
- `sessions.is_return` boolean not null default false (первые 4 сессии
  пересобранного цикла).

Правила:

- перенос не создаёт новую версию плана;
- `RETURN_1`/`RETURN_2` создают новую версию плана;
- пересборка создаёт новый цикл и версию плана v1;
- каждое действие пишет audit;
- старые циклы и версии не удаляются.

## 5. API и UI

- `POST /api/sessions/:id/reschedule`:
  `{ newDate: "YYYY-MM-DD", mode: "SINGLE" | "SHIFT_TAIL" }`.
- `POST /api/cycles/:id/review`:
  `{ action: "REBUILD" | "STOP", reason: "LONG_PAUSE" | "ILLNESS" | "USER" }`.
- На «Сегодня»: кнопка «Отложить» рядом с «Начать»; дата, конфликт порядка и
  предложение сдвинуть хвост.
- После длинной паузы: экран пересмотра вместо кнопки старта.
- В сессии возвращения: заметный бейдж «Возвращение» и RIR 3–4.

## 6. Критерии приёмки

1. Перенос одной сессии не меняет назначения и не создаёт версию плана.
2. Конфликт порядка возвращает `409 ORDER_CONFLICT`.
3. `SHIFT_TAIL` сдвигает даты и конец цикла; продление > 14 дней запрещено.
4. Пауза 8–13 дней даёт `RETURN_1`, 14–27 — `RETURN_2`, оба с подтверждением.
5. Пауза ≥ 28 дней блокирует старт и требует пересмотра.
6. `REBUILD` закрывает старый цикл, создаёт новый с возвратным фазовым режимом
   и сохраняет audit.
7. `STOP` закрывает цикл и ведёт в онбординг.
8. Болезнь/красный флаг не обходит safety-паузу.
9. Все сценарии покрыты тестами: unit, API, E2E.

## 7. Реализация P0 (25.10.2026)

### 7.1. Миграция

`0002_superb_trauma.sql` добавляет ровно четыре поля из раздела 4. Миграция
применена на чистой `chiron_test` и на dev-БД; seed не менялся.

### 7.2. Перенос

- Чистая проверка границ и порядка — `packages/core/src/reschedule.ts`.
- Сервис — `apps/web/src/lib/reschedule-service.ts`, строки цикла блокируются
  `FOR UPDATE`.
- `SINGLE` проверяет ближайшую следующую `PLANNED`-сессию; равенство дат уже
  считается конфликтом.
- `SHIFT_TAIL` двигает текущую и все последующие `PLANNED`-сессии, конец цикла
  и считает суммарное продление от базовых 8 недель. Лимит — 14 дней.
- `rescheduled_from` хранит первую исходную дату; повторный перенос её не
  перезаписывает.
- Audit `SESSION_RESCHEDULED` содержит `from`, `to`, `mode`, `deltaDays`,
  `endDateBefore`, `endDateAfter`, `movedSessions`. Имена `endDateBefore/After`
  выбраны вместо `cycleEndDateBefore/After` и одинаковы в API, audit и UI.
- Версия плана и назначения не меняются; это проверено unit- и E2E-тестами.

### 7.3. Пауза и возврат

- Классификатор — `packages/core/src/pause.ts`: 0–7 `NONE`, 8–13 `RETURN_1`,
  14–27 `RETURN_2`, ≥28 `LONG`.
- Safety-пауза активна, пока после последнего неразрешённого сигнала не
  завершена новая сессия. Учитываются последний RED safety event, последняя
  принятая `PAUSE`-рекомендация и последняя запись болезни (`SIGNS` или
  `CONFIRMED`). Дата сигнала приводится к локальной календарной дате приложения,
  как и `todayIso()`, иначе UTC-полночь рассинхронизирует день.
- Safety-пауза < 14 дней даёт `SAFETY`: старт заблокирован, доступен ручной
  пересмотр с safety-предупреждением. ≥ 14 дней — `LONG` и обязательный
  пересмотр.
- `prepareReturn` создаёт **scoped**-версию плана и привязывает её только к
  возвратным сессиям. `currentPlanVersionId` остаётся на обычной ветке, чтобы
  RIR 3–4 и снижение нагрузки не протекали в последующие сессии. Следующая
  версия нумеруется как `max(version) + 1`, а `is_return`-сессии исключены из
  перепривязки при последующих решениях.
- Для `RETURN_1/2` целевой RIR хранится в scoped-версии (3 или 4/3). Для
  пересобранного цикла v1 остаётся обычной, а UI показывает «RIR 3–4» для
  `is_return`-сессий; правило `RETURN_PHASE` всё равно блокирует прогрессию.
- Экспозиции возврата помечаются `duringReturn`; сравнение на снижение и
  подтверждение верхней границы не смешивают возвратные и обычные экспозиции.
  Это предотвращает ложный `LOCAL_REDUCE`/`DELOAD` сразу после возврата.
- Старт блокируется: `RETURN_REQUIRED` для 8–27 дней без подготовленного
  возврата, `CYCLE_REVIEW_REQUIRED` для `LONG`, `SAFETY_PAUSE` для активного
  safety-сигнала.
- Повторный возврат без новой паузы возвращает `409 ALREADY_RETURN`; при
  подготовке возврата старые `PENDING`-рекомендации истекают.

### 7.4. Пересмотр и пересборка

- `reviewCycle` блокирует строку цикла, требует `ACTIVE` и поэтому идемпотентен:
  повторный вызов получает `409 CYCLE_NOT_ACTIVE`.
- `STOP` закрывает цикл как `STOPPED` с `close_reason` и ведёт в онбординг.
- `REBUILD` копирует варианты, подсобку, эстетику, роли и связи из
  `currentPlanVersionId`, применяет множитель и создаёт новый цикл на 8 недель.
- Множитель: ≤13 дней — 100%, 14–42 — 90%, 43–84 — 80%, 85–168 — 70%,
  >168 — калибровка (`null`, без подстановки веса). Полоса 14–27 дней попадает
  в консервативные 90%.
- Первые 4 сессии нового цикла получают `is_return = true`, а
  `return_phase_sessions = 4`. Прогрессия в них блокируется правилом
  `RETURN_PHASE`.
- Пересборка создаёт рекомендацию `REBUILD`, решение, версию плана v1, audit
  `CYCLE_REVIEWED` на старом цикле и `CYCLE_REBUILT` на новом.
